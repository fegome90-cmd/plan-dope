# Plan Validation

## Overview

This skill performs **fail-closed validation** of complete plans, ensuring all YAML files conform to schemas, traceability chains are intact, constraints are satisfied, and the plan is ready for execution. Invalid plans are **rejected** - never passed through.

**Key capabilities:**
- Schema validation for all YAML files (RequirementSet, WorkOrder, PlanTree)
- Traceability checking (requirements → strategies → WOs)
- Constraint satisfaction verification
- Dependency cycle detection
- Scope conflict detection
- DoD completeness validation

## Terminology

- **Fail-Closed** - Invalid plans are rejected, never passed through
- **Traceability** - Chain: claims → strategies → plan tree → WOs → DoD
- **Schema Validation** - YAML structure and required field checking
- **Scope Conflict** - Overlapping allow/deny lists between WOs
- **DoD Completeness** - Each WO has 2+ verification commands with quantifiable thresholds
- **Circular Dependency** - WOs that depend on each other in a cycle
- **PlanPack** - Complete validated plan ready for work_O execution

## When to Use

**Invoke this skill when:**
- All phases complete (requirements, strategies, plan tree, WOs)
- User manually edits plan files
- User asks "is this plan valid?" or "validate this plan"
- Command `/plan-orch` is invoked (Phase 5)
- `/plan-validate` command is run

**Trigger phrases:**
- "Validate this plan"
- "Check if plan is valid"
- "Review plan for issues"
- "Is this ready to execute?"

## Process

### Step 1: Locate Plan Files

**Find all plan artifacts** for given PLAN ID:

**Expected structure:**
```
_ctx/plans/PLAN-YYYY-NNNN/
├── requirements.yaml
├── strategies/
│   └── strategy-evaluation.yaml
├── plan-tree.yaml
├── work_orders/
│   ├── WO-0001.yaml
│   └── ...
└── validation-report.yaml  # Generated by this skill
```

**If critical files missing:**
- Fail immediately with clear error
- List which files are missing
- Do not proceed with validation

### Step 2: Run Schema Validation

**Use `plan_validator.py` script** to validate YAML schemas:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/plan_validator.py \
  _ctx/plans/PLAN-2026-0001/requirements.yaml \
  --schema requirement-set

python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/plan_validator.py \
  _ctx/plans/PLAN-2026-0001/plan-tree.yaml \
  --schema plan-tree

python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/plan_validator.py \
  _ctx/jobs/WO-0001.yaml \
  --schema work-order
```

**Check results:**
- Exit code 0 = PASS
- Non-zero exit code = FAIL (reject plan)

**Report schema validation:**
```
✅ Schema Validation: PASS
- requirements.yaml: Valid RequirementSet
- plan-tree.yaml: Valid PlanTree
- WO-0001.yaml: Valid WorkOrder
...
```

### Step 3: Check Traceability

**Use `traceability.py` script** to verify requirement → strategy → WO chains:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/traceability.py \
  _ctx/plans/PLAN-2026-0001
```

**Traceability checks:**

**Requirement → Strategy:**
- Every claim in RequirementSet is addressed by selected strategy
- No orphaned requirements

**Strategy → Plan Tree:**
- Selected strategy (STRAT-XXX) exists in strategy-evaluation.yaml
- Plan tree references valid strategy ID

**Plan Tree → Work Orders:**
- Every WO in plan-tree.yaml has corresponding WO-*.yaml file
- Every WO-*.yaml is referenced in plan-tree.yaml

**WO → DoD:**
- Every WO has corresponding DoD file (dods/WO-XXXX-dod.yaml)
- Every DoD references valid WO ID

**Dependencies:**
- All WO dependencies reference valid WO IDs
- No circular dependencies (WO-A → WO-B → WO-A)

**Report traceability:**
```
✅ Traceability: PASS
- All [N] claims addressed by strategy
- All [M] WOs in plan tree have YAML files
- All DoDs reference valid WO IDs
- No circular dependencies detected
```

### Step 4: Detect Missing Dependencies

**Use `dependency_inference.py` script** to auto-detect missing dependencies:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/dependency_inference.py \
  _ctx/plans/PLAN-2026-0001/work_orders \
  --confidence-threshold 0.7
```

**Detection methods:**
- **Create→Modify pattern:** WO-0002 modifies files created by WO-0001
- **Import usage:** WO-0003 imports `src.auth.models` (created by WO-0001)
- **API endpoints:** WO-0004 tests `/api/auth/refresh` (requires WO-0002)

**Report dependency inference:**
```
⚠️  Dependency Inference: [N] suggestions found

HIGH CONFIDENCE (≥ 0.8):
  WO-0002 → WO-0001 (confidence: 0.95)
    Reason: create→modify pattern detected
    Evidence:
      - WO-0001 allows: src/auth/models.py
      - WO-0002 allows: src/auth/login.py (imports User model)

MEDIUM CONFIDENCE (0.5-0.8):
  WO-0004 → WO-0002 (confidence: 0.75)
    Reason: API endpoint dependency
    Evidence:
      - WO-0004 tests: /api/auth/refresh
      - WO-0002 provides: /api/auth/login
```

**Action required:**
- **High confidence (≥ 0.8):** Consider adding to dependencies
- **Medium confidence (0.5-0.8):** Review before adding
- **Low confidence (< 0.5):** Manual review required

**Update WO files if needed:**
```bash
# Edit WO-0002.yaml to add dependency
dependencies:
  - WO-0001  # User model (detected by dependency inference)
```

### Step 5: Validate Objective/DoD Consistency

**Use `consistency_validator.py` script** to cross-validate objectives and DoD:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/lib/consistency_validator.py \
  _ctx/plans/PLAN-2026-0001/work_orders \
  --fuzzy-threshold 0.6
```

**Consistency checks:**
- **Missing keywords:** Objective mentions "rotation" but DoD doesn't validate it
- **Quantitative mismatches:** Objective says "< 100ms", DoD says "< 200ms"
- **Contradictions:** Objective says "remove endpoint", DoD tests it works
- **Vague thresholds:** DoD threshold is "fast" instead of "< 100ms"

**Report consistency validation:**
```
Consistency Validation: PLAN-2026-0001
Analyzed [N] Work Orders
Overall Score: [X]%

❌ CRITICAL:
  WO-0007: "rotation" in objective but not in DoD
    Suggestion: Add DoD entry testing rotation schedule

⚠️  HIGH:
  WO-0012: Objective "< 100ms", DoD "< 200ms"
    Suggestion: Align threshold with objective
```

**If inconsistencies found:**
- **Critical issues → Block validation**, require fixes
- **High severity → Warning**, recommend fixes
- **Medium/Low → Informational only**

### Step 6: Verify Constraint Satisfaction

**Check selected strategy** against constraints from RequirementSet:

**For each constraint:**
1. Read constraint from requirements.yaml
2. Check if strategy satisfies it
3. If `hard: true`, strategy MUST satisfy
4. If `hard: false`, note as warning if not satisfied

**Example checks:**
```yaml
# Constraint from requirements.yaml
- id: CN-001
  type: timeline
  description: "Must launch by end of Q1 2026"
  hard: false

# Strategy evaluation
- strategy: STRAT-001
  constraint_satisfaction: 4  # 1-5 scale
  timeline_assessment: "Can ship by Q1 with focused scope"
```

**Report constraints:**
```
✅ Constraints: PASS
- CN-001 (timeline): STRAT-001 score 4/5 - Can meet deadline
- CN-002 (budget): STRAT-001 score 5/5 - Within budget
- CN-003 (tech stack): STRAT-001 score 5/5 - Uses required Python 3.12+
```

**If hard constraint violated:**
```
❌ Constraints: FAIL
- CN-001 (timeline): STRAT-002 score 2/5 - Cannot meet Q1 deadline (hard constraint)

**Plan REJECTED** - Hard constraint not satisfied.
```

### Step 7: Validate DoD Completeness

**Check every WO's Definition of Done:**

**For each DoD file:**
- At least 2 verification commands
- All thresholds are quantifiable (numbers, percentages, etc.)
- All verification commands are syntactically valid
- Commands reference files that exist

**Example validation:**
```yaml
# Good DoD
definition_of_done:
  - metric: "API latency"
    threshold: "< 100ms p95"
    verification: "python tests/test_api_perf.py --benchmark"  # Valid

# Bad DoD (would fail)
definition_of_done:
  - metric: "Performance"
    threshold: "fast"  # Not quantifiable
    verification: "echo 'done'"  # Not a real verification
```

**Report DoD validation:**
```
✅ DoD Completeness: PASS
- All [N] WOs have ≥2 verification commands
- All thresholds are quantifiable
- All commands reference valid test scripts
```

### Step 8: Detect Scope Conflicts

**Check for overlapping or conflicting scope boundaries:**

**For each pair of WOs:**
- If both have same `allow` paths → flag as potential conflict
- If WO-A has `deny` path that WO-B has `allow` → flag as conflict

**Example conflict:**
```yaml
# WO-0001
scope:
  allow: ["src/auth/"]
  deny: ["src/auth/oauth/"]

# WO-0005
scope:
  allow: ["src/auth/oauth/"]  # CONFLICT: WO-0001 denies this
  deny: []
```

**Report scope conflicts:**
```
❌ Scope Conflicts: FAIL
- WO-0001 denies src/auth/oauth/ but WO-0005 allows it

**Plan REJECTED** - Resolve scope conflicts before validation.
```

**Target files for review:**
- All WorkOrder YAML files (structure, clarity)
- Verification commands in DoD entries (bash, pytest, curl syntax)
- Any Python test scripts referenced in DoD

**Invoke code review:**
```
/code-review _ctx/plans/PLAN-2026-0001/work_orders/
```

**Review criteria:**
- YAML structure clarity and consistency
- Bash command syntax correctness
- Test command validity (pytest, curl, etc.)
- Security best practices (no hardcoded secrets, proper escaping)
- Error handling in verification commands

**Report code review:**
```
✅ Code Quality Review: PASS
- All WO YAML files: Well-structured and clear
- Verification commands: Syntactically valid
- Bash commands: Proper quoting and error handling
- No security concerns detected
```

**If issues found:**

## Tone and Style

**Be firm about quality:**
- "This plan cannot proceed - [issue] must be fixed."
- "Validation failed - [N] critical errors detected."
- "All checks passed - plan is ready for execution."

**Be specific about failures:**
- "File: _ctx/jobs/WO-0003.yaml:5 - missing 'objective' field"
- "Circular dependency: WO-0001 → WO-0002 → WO-0001"

**Be helpful with fixes:**
- "To fix: Add objective field to WO-0003.yaml"
- "To fix: Remove WO-0002 from WO-0001's dependencies"

## Fail-Closed Principle

**ALWAYS reject invalid plans:**
- Never pass through plans with critical errors
- Never auto-fix issues without user approval
- Require explicit user action to fix failures

**What requires rejection:**
- Schema validation failures
- Circular dependencies
- Hard constraint violations
- Scope conflicts
- Missing critical files
- Invalid traceability chains

**What generates warnings but allows:**
- DoD with only 1 verification command (recommend 2+)
- Soft constraint violations
- Minor formatting issues
- Code quality issues that don't affect functionality
- Opportunities for simplification (optional to apply)

## Common Validation Failures

### Schema Failures
```yaml
# Missing required field
WorkOrder:
  id: WO-0001
  # objective field missing
```

### Traceability Failures
```yaml
# WO references non-existent epic_id
WorkOrder:
  epic_id: E-999  # E-999 doesn't exist in plan-tree.yaml
```

### Constraint Failures
```yaml
# Hard constraint violated
constraints:
  - id: CN-001
    type: timeline
    hard: true
# But selected strategy cannot meet timeline
```

### Dependency Cycles
```yaml
# WO-0001 depends on WO-0002, which depends on WO-0001
dependencies: [WO-0002]  # In WO-0001.yaml
dependencies: [WO-0001]  # In WO-0002.yaml
```
